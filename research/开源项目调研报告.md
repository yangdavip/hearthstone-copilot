# 炉石传说 AI 助手（macOS）— 开源项目调研报告

调研日期：2026-10-09
调研目标：为「读取 macOS 炉石对战数据流 → 理解场面 → 大模型辅助决策」寻找可复用资产

---

## 一、结论先行

**推荐技术路线：Power.log 日志解析（而非内存读取 / 截屏 OCR）**

理由（本机已验证）：

- 你的 Mac 上 `/Applications/Hearthstone` 已安装，且 `~/Library/Preferences/Blizzard/Hearthstone/log.config` **已经开启 `[Power]` 段且 `Verbose=true`**
- 现有日志 `Logs/Hearthstone_2026_08_12_20_55_43/Power.log` 有 **10.2 MB / 85,475 行 / 10 场对局**
- 日志中**直接带中文卡名**，无需额外 OCR 或卡牌 ID 映射表：

```
D 22:15:36.7002360 PowerTaskList.DebugPrintPower() -         TAG_CHANGE Entity=[entityName=扛包收尸人 id=242 zone=PLAY zonePos=6 cardId=RLK_503 player=1] tag=DAMAGE value=2
```

- 事件类型齐全：`CREATE_GAME` / `CHANGE_ENTITY` / `TAG_CHANGE`（36,380 条）/ `Block Start|End`（各 1,226+）
- 含 `SECRET` 字段 303 处 → 奥秘可追踪

**唯一必须先修的问题**：日志被截断。

```
=== Truncating log, which has reached the size limit of 10000KB ===
```

10MB 封顶，长对局后半段数据会丢。修复方式（写入 `/Applications/Hearthstone/client.config`，目前该文件不存在）：

```ini
[Log]
FileSizeLimit.Int=-1
```

## 二、GitHub 重点项目评估

### 1. OstrichHermit/hearthstone-cli ⭐⭐⭐⭐⭐ 最贴合需求

**定位**：专为 AI Agent 设计的炉石 CLI 工具箱，MIT 协议，有 PyPI 包。

与本项目需求几乎 1:1 对应，四大能力：

| 能力 | 说明 | 对我们的价值 |
|---|---|---|
| `hs board` | 全量重放 Power.log packet，输出结构化实时面板 | **核心直接复用** |
| `hs watch` | 后台 tail Power.log，换牌阶段 + 我方回合时推送提示词触发 AI 分析 | **核心直接复用** |
| deckstring 编解码 | 完整支持，含副牌库三元组、动态卡组容量（阿扎莉娜20 / 拉法姆40） | 直接可用 |
| 构筑规则校验 | 数量/传说限量/职业限定/标准池白名单 | 直接可用 |

面板已覆盖的字段（正是你要的「理解场面」）：
- 对局模式、总手数/回合/当前行动方
- 双方法力（`可用/总（已用N）`，过载锁定单列）+ 先后手（后手标注硬币）
- 双方英雄血/甲/武器/技能（技能被灌注/变形时显示新技能）
- 场面随从与地标：嘲讽/圣盾/风怒/冻结/休眠/潜行/扰魔 等状态标注
- 我方手牌：费用/攻/血，含**兆示预览**、已强化/不可打出标注
- 双方牌库剩余数 / 疲劳 / 尸体数
- 任务进度槽、终局胜负与结束方式（斩杀/投降/疲劳）

「战况回放」功能带最近 3 个回合的完整事件流，卡牌效果描述**全量不截断并按「入手一次」挂载**——作者明确说明「AI 无需查库即可理解新扩展」。这直接解决了我们最担心的问题：新版本出卡，LLM 不认识。

**局限**：
- `hs watch` 的 IM 桥接器是私有组件，不在仓库内（默认 `http://127.0.0.1:8088`），需自建
- `hs collection`（读游戏内存同步收藏卡组）**仅 Windows**
- macOS 路径需自行适配（作者未在文档中明示 macOS 实测）

### 2. HearthSim/python-hslog ⭐⭐⭐⭐⭐

Power.log 的事实标准解析库，MIT 协议，HearthSim 官方出品，**1.20.0 发布于 2026-08-15**（活跃维护）。

把原始日志转成结构化 Python 对象：`Packet` / `Block` / `TagChange` / `FullEntity`，每条携带毫秒时间戳、game frame、entity ID、TAG、新旧值。可精确追溯任意卡牌任意时刻的血量/攻击力/是否沉默/是否冻结。

**建议**：作为我们状态还原层的解析内核，比自己写正则可靠一个数量级。

### 3. jleclanche/fireplace ⭐⭐⭐⭐

Python 炉石**规则模拟器**，AGPLv3。2776 commits，HearthSim 官方。

价值：可以做**离线推演**——给定当前场面 + 候选出牌，模拟后续回合验证 LLM 建议是否真的合理。也可用 MCTS 搜索。

**局限（重要）**：卡牌实现**停留在 Patch 17.6（2019 年）**，当前游戏已到 36.x。只能用于「规则框架参考」和「自建卡牌效果子集」，**不可直接依赖**。

### 4. HearthstoneJSON ⭐⭐⭐⭐⭐（数据基础设施，必需）

卡牌数据的行业标准来源，`api.hearthstonejson.com/v1/latest/zhCN/cards.json`，UTF-8，中文本地化。

单条卡牌含：`id` / `dbfId` / `name` / `text`（中文效果文本）/ `cost` / `attack` / `health` / `mechanics[]`（关键词）/ `cardClass` / `classes[]`（多职业卡）/ `rarity` / `set` / `type` / `referencedTags`（可识别「本卡引用了奥秘」这类逻辑）。

补丁日刷新即可。**注意**：log 里的 `entityName` 已是中文，可直接与本表 `name` 匹配，无需走 dbfId。

### 5. HearthSim/HSTracker ⭐⭐⭐⭐（macOS 原生，强烈建议直接装）

**HearthSim 官方 macOS 客户端**，MIT 协议。最新版 3.6.13，2025-12-13 更新至炉石 34.2.2。

- 原生 Swift/ObjC，实时悬浮窗，Apple Silicon 原生支持
- `brew install --cask hstracker` 一键安装
- 自动识别当前卡组、显示双方剩余卡牌、胜率统计
- **对 macOS 而言这是零成本的第一阶段成果**——先用它拿到 80% 的「场面理解」，我们专注做 LLM 军师层

**局限**：Swift/ObjC，与我们的 Python 技术栈割裂；无法直接读出其内部状态给 LLM。但可作为「用户侧参考面板」并存。

### Gitee / 国内生态

- `cfanc/hearthstoneRoutine`（炉石兄弟策略）— 只有策略 C# 代码，不含主程序，且明确声明违反暴雪协议

- **结论：国内没有可直接复用的 macOS + 日志解析 + LLM 方案**，需自建

## 三、技术选型建议

```
数据采集   Power.log 增量 tail（python-hslog 解析内核）
           + 先补 client.config 解除 10MB 截断
状态模型   实体-标签状态机：Entity{id,name,cardId,zone,zonePos,player,tags}
           从此模型投影出 BoardState（双方英雄/武器/场面/手牌/牌库）
卡牌知识   HearthstoneJSON zhCN，补丁日增量刷新
牌库推演   deckstring 解码 → 起手留牌策略；未见卡集合 → 抽牌概率分布
决策层     LLM（OpenAI 兼容接口，可指向国内模型）
           输入：结构化 JSON 局面 + 双方套牌 + 近 3 回合事件流
           输出：推荐出牌序 / 斩杀判定 / 留牌 / 风险提示
呈现层     macOS 置顶悬浮窗（PyObjC），高亮手牌编号 + 语音播报
```

### 关于「自动操作」的边界（必须明确）

暴雪用户协议 1.C.ii.2 明确禁止 BOT。本项目应定位为**辅助决策（只读日志 + 只给建议，操作由人类执行）**：
- ✅ 读日志、算概率、给建议、高亮提示 —— 属于卡牌跟踪器（HDT/HSTracker）范畴，社区普遍存在
- ❌ 模拟点击、鼠标键盘操作、进程注入 —— 明确违规，暴雪有检测与封禁能力

本方案全程只读日志，不注入不模拟输入，风险可控。这也恰好是「辅助对战」而非「托管」的定位。

### 6.2 最有价值的对照：`barnabys-drew` 的 live-coach 清单

它的 `hearthstone-live-coach/README.md` 把真实对局踩过的坑写成了 checklist，与本项目这几天独立修复的问题**几乎逐条对应**，可视为对本工具设计的一次外部验证：

| 它的规则 | 本项目的对应实现 |
|---|---|
| "Exhausted ≠ Locked Down"：疲劳随从下回合会满血攻击（作者记录「14/8 疲劳随从下回合打了 28，输了一局」）；计算来袭伤害时把疲劳随从当满威胁 | `Entity.attack_status()` 区分我方「本回合能否攻击」与对手「下回合能否攻击」；`estimate_board_value` 按威胁口径评估 |
| "Your turn only"：`== TURN.*your turn` 才触发，对手回合静默 | 统一判据 `is_my_action_phase()` + 玩家级 TURN 名字判据 + `gap >= 2` 硬约束 |
| "Card Text Over Memory"：快照里每张卡带 `type` / `text`，禁止用模型记忆猜效果 | `describe_entity()` 按日志 `cardId` 精确匹配中文卡表，标注匹配来源 |
| "Use card text, never from memory" / LOCATION 有冷却、SPELL 要目标 | 地标单列 + 剩余耐久 + 本回合是否可用 |
| Lethal 先列算术、攻击先于法术（亡语可能改变场面） | `detect_lethal` 只统计可打脸伤害并列出未计入名单；`legal_play_combos` 枚举合法费用组合 |
| "Fresh snapshot"：每回合重读 `live.json`；**每轮 poll 用全新 `LogParser()`**，因为一份日志含多局会污染单个 parser | `follow_latest` 切日志时整体重建 recon；槽位映射残留修复 |
| 已知陷阱：发现牌滞后一回合、亡语结算滞后 | 本项目尚未专门处理，可列为待办 |

**关键差别**：这些开源项目大多把规则写成 `SKILL.md` / 提示词的**软约束**，靠模型自觉遵守；本项目已把它们做成**代码级确定性校验**（`attack_status` / `_validate_mana` / `_validate_attack` / `_validate_readiness` / 回合间隔闸）。在「模型算术不可靠」这一点上，本项目的做法更稳。

### 6.3 值得借鉴的增量（按性价比排序）

1. **校验器驳回 → 自动改正一次**（`lscs-public`）：模型回答解析失败或方案过不了校验器时，把「钱不够 / 场面放不下 / 编号不存在」等具体原因回传一次让其重写（多轮对话复用前缀缓存，每请求最多一次）。本项目现在是「置顶警告、人工让步」，改成自动改正能直接提升建议可用率。
2. **脱敏层**（`CuZaoo`）：发给模型前移除玩家名、原始 tag、时间戳，只保留「我方 / 对手」。本项目目前把 `player_name` 原样写进 payload，既是隐私暴露也让模型容易用名字猜身份。
3. **结构化输出三层降级**（`CuZaoo`）：`json_schema` → `json_object` → 本地校验，替换当前单一 `_parse()` 正则抽取。
4. **双层决策架构**（`Chshiro` / `HearthCoach`）：让确定性引擎枚举合法动作并算分，LLM 只做战略取舍与解释。这是解决「模型费用/斩杀算错」的根治方向，但改造量最大。
5. **提示词补全陷阱清单**（`barnabys` checklist）：风怒 ×2、圣盾先破、嘲讽阻挡、亡语别乱触发、发现牌滞后、牌库剩余 outs 影响竞速、对手已用解牌则压上。
6. **复盘与采纳率**（`CuZaoo` / `bg-coach` / `barnabys`）：保存每回合建议与回合后实际局面差，统计采纳率、沉淀 lessons，做赛后复盘。
7. **成本/延迟优化**（`lscs`）：把系统提示 + 卡池/对手摘要做成跨回合不变的前缀命中缓存；把快速建议与深度分析分频。

### 6.4 是否改用 `python-hslog` 作为解析内核？

**当前不建议。** 虽然 87★ 且 2026-08 仍维护，但 `barnabys-drew` 的实时方案是「每 3 秒 poll 就用全新 `LogParser()` 重放当前对局缓冲」——在增量实时场景下并不比本项目的实体-标签状态机更省，且会丢失本项目已用真实日志逐项验证的中文卡名、卡号精确匹配、召唤失调、身份配对等定制逻辑。若未来炉石日志格式大改、自研正则维护成本过高，可把 `hslog` 作为「离线回放校验器」引入（拿它的 EntityTreeExporter 结果与本工具对账），而不是直接替换在线链路。

### 6.5 合规一致性

上述同赛道项目（CuZaoo、lscs、HearthCoach、barnabys、YinshawnRao 的 WPF 记牌器）都在 README 里明确写了「只读日志、不读内存、不注入、不自动点击」，与本报告第一节的定位一致。少数老项目（截屏 + 自动点击 Bot、内存读取型插件）不在此列，不建议参考。
